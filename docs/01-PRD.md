## Product name and one-sentence idea

**ClinicSystem EG** هي منصة SaaS واحدة متعددة العيادات والتخصصات، يُنشئ فيها مالك المنصة (Super Admin) لكل عيادة مساحة معزولة برابط فرعي مثل `ahmad.clinicsyseg.com`، ويحدد تخصصها وميزاتها من لوحة تحكم مركزية، دون نسخ الكود لكل عميل.

## Target users

| المستخدم | من هو | ما الذي يحتاجه |
|---|---|---|
| **Super Admin / مالك المنصة** | فريق ClinicSystem EG | إنشاء العيادات وتخصيصها وإيقافها وإدارة اشتراكاتها من لوحة واحدة، مع سجل تدقيق |
| **Clinic Admin / مدير العيادة** | صاحب العيادة أو مديرها | إدارة فروع عيادته وموظفيها ودعوتهم بنفسه، وإعدادات العيادة والتقارير |
| **Receptionist / الاستقبال** | موظف الاستقبال في فرع | تسجيل المرضى، الحجز، التحصيل |
| **Doctor / طبيب** | طبيب في العيادة | السجلات والزيارات والتشخيصات والوصفات ضمن تخصص العيادة |
| **Therapist / معالج** | أخصائي علاج طبيعي | الجلسات العلاجية وخطط العلاج ومتابعة التقدم |
| **Other staff** | أدوار تشغيلية أخرى | أقل صلاحية لازمة لأداء المهمة |

## Problem and current workaround

- **المشكلة:** النظام الحالي (كينيتك) مبني لعيادة علاج طبيعي واحدة: جدول `clinic_settings` بسجل وحيد (`id = 1`)، ولا يوجد `organization_id` في الجداول، وصلاحيات RLS تعتمد على دور عام في جدول `staff`. لا يمكن تقديمه لعيادة ثانية دون نسخة منفصلة من الكود وقاعدة البيانات.
- **الحل البديل اليوم:** نشر نسخة يدوية لكل عميل، أو تعديل الكود لكل تخصص. هذا مكلف ويصعب صيانته، ويزيد خطر تسرب البيانات بين العملاء.

## Goal and success measure

| الهدف | مقياس النجاح القابل للتحقق |
|---|---|
| إدارة مركزية | Super Admin ينشئ عيادة (اسم، slug، تخصص، ميزات، حالة، أول مدير) في أقل من 5 دقائق من لوحة واحدة |
| عزل البيانات | 100% من اختبارات الوصول المتبادل تفشل: مستخدم العيادة A لا يقرأ/يعدّل أي سجل للعيادة B عبر API أو SQL/RLS أو Storage |
| توجيه صحيح | بعد الدخول من `clinicsyseg.com` يصل المستخدم لعيادته، أو لشاشة اختيار العيادة إن كان عضوًا في أكثر من عيادة |
| تخصيص دون إصدار جديد | تغيير ميزات أو تخصص عيادة ينعكس على واجهتها وصلاحياتها فورًا دون نشر نسخة جديدة |
| استمرار النظام الحالي | ترحيل بيانات العيادة الحالية بنسخة احتياطية واختبارات مطابقة (عدد السجلات والعلاقات والملفات) دون فقد أي سجل |
| قابلية التدقيق | كل عملية إدارية حساسة مسجلة في `audit_events` (المنفذ، التوقيت، الهدف، النتيجة) |
| سرعة التحميل | أول شاشة تظهر خلال **≤ 1 ثانية** على جهاز متوسط (معالج أبطأ 4×). **مقاس حاليًا:** 370 ms، وكان 24.8 ثانية قبل الترجمة المسبقة ([07](07-Performance-Audit.md)) |
| اكتمال البيانات | كل الشاشات تعرض كل السجلات حتى لو تجاوز عددها حد *Max rows* في Supabase (1000 افتراضيًا). **مطبّق:** تحميل الصفحات بعد الحد |

## Out of scope for version one

- الدفع الإلكتروني التلقائي والاشتراكات المتكررة (الإدارة يدوية من لوحة Super Admin أولًا).
- تطبيق جوال مستقل أو نسخة كود منفصلة لكل عيادة.
- نطاق مخصص لكل عيادة (مثل `myclinic.com`) أو بريد إلكتروني على نطاق العيادة.
- تعدد التخصصات للعيادة الواحدة (التصميم يسمح به لاحقًا، لكنه غير مفعل).
- ملفات طبية أو وصفات مولدة آليًا دون مراجعة الطبيب، أو تشخيص طبي آلي.
- التكاملات غير المعتمدة رسميًا: بوابات الدفع، التأمين، المختبرات.
- بوابة المريض (اختيارية لاحقًا).
- التسجيل الذاتي للعيادات من الواجهة العامة (إنشاء العيادات حكر على Super Admin).

## User stories

**Super Admin**
- As a Super Admin, I want to create a clinic with a name, unique slug, specialty, and first admin email, so I can onboard a new customer without touching code.
- As a Super Admin, I want to enable or disable modules per clinic, so I can match the clinic's plan and needs.
- As a Super Admin, I want to suspend a clinic with a recorded reason, so I can block access immediately while keeping its data for 6 months.
- As a Super Admin, I want to set a clinic's plan and subscription status manually, so I can manage billing before online payment exists.
- As a Super Admin, I want to search the audit log by clinic, user, action type, and date, so I can investigate any sensitive change.

**Clinic Admin**
- As a Clinic Admin, I want to invite staff by email and assign their role and branches, so I can build my team without waiting for the platform.
- As a Clinic Admin, I want to add and manage branches (name, address, phone, working hours), so each branch runs its own schedule.
- As a Clinic Admin, I want to deactivate a staff member's membership, so they lose access immediately without losing their history.

**Clinic staff**
- As a staff member in more than one clinic, I want to pick the clinic after logging in, so I only see the data of the clinic I'm working in.
- As a receptionist, I want to book an appointment for a patient in my branch, so the schedule of each branch stays accurate.
- As a therapist, I want to see only the modules my clinic has enabled, so the interface matches my specialty.

2. ماذا يحدث للبيانات بعد انقضاء الـ 6 أشهر (حذف نهائي أم أرشفة)، وما طريقة التصدير وطلب الاستعادة؟
3. ما وحدات طب الأسنان والطب العام المطلوبة فعلًا في الإصدار الأول، ومن صاحب الاعتماد السريري لكل وحدة؟
4. الأرقام الفعلية لحدود كل خطة (تُحدد تجاريًا؛ النظام يدعم الضبط فقط).
5. سياسة تغيير الـ slug: هل يُسمح به، وهل تُوجّه الروابط القديمة أم تُبطل؟
6. ~~الوجهة النهائية لقاعدة البيانات~~ — **حُسم (21 أكتوبر 2026): نقل كل شيء إلى hosting.com** (PostgreSQL + Node.js API). التفاصيل في [TRD](02-TRD.md) و [08](08-Hosting-Migration.md).
7. إصدار PostgreSQL و Node.js وحدود الموارد على خطة hosting.com الحالية (المهمة 1.15).
8. هل يُبطل «تسجيل الخروج» الجلسة على الخادم؟ اليوم يُمسح الـ cookie فقط، ونسخة مسروقة منه تبقى صالحة حتى انتهائها (12 ساعة أو 30 يومًا).
9. هل يتطلب تغيير كلمة المرور إدخال كلمة المرور الحالية؟ (اليوم لا، حسب العقد.)
10. هل يُسمح بإغلاق عيادة `pending_activation` لم تُفعّل أبدًا؟ (الانتقالات الحالية لا تسمح.)
11. الحد الأدنى لكلمة المرور: الـ API يطبق 6 أحرف (كالنظام الحالي)، و App Flow ذكر 8 لقبول الدعوة. أيهما؟
12. الوحدات المعطلة تُفرض الآن في الواجهة **والـ API** (`403 module_disabled`، والبيانات محفوظة). هل تُفرض داخل قاعدة البيانات أيضًا (المهمة 2.16)؟
13. صفحات الدعوة المنتهية أو الملغاة تطلب من المستخدم التواصل مع مدير العيادة. هل نحتاج زر «اطلب دعوة جديدة» (يحتاج مسارًا جديدًا في الـ API)؟
